## Field test triage: 2.0 (4) ran

xian tested outdoors on 09-20 and filed four findings with ten screenshots in `testing/`. **It did
not crash and the loop ran end to end.** First usable build in the train.

Read the screenshots before reading his summary, which was the right order: the diagnostics panel in
`IMG_5374` turned two impressions into measurements. `heard 100.8s — user 75.7 / other 25.1 /
silence 0.0`, with `user -32.8 / ambient -42.5 / threshold -38.1 / floor -48.5`.

**`silence 0.0` is the finding.** The floor was `ambient - 6.0` and ambient is measured with the user
quiet, so a moment *at* ambient is nobody talking, and the floor was unreachable outdoors. Every
buffer scored as speech; "other speaking" absorbed the room. Fixed to `ambient + 3.0`. Raised the
usability bar from 8 dB to 12 with a marked 12-16 band: 8 separates two buckets, not three, and his
9.7 dB run produced a number he correctly disbelieved. **Said in the code that 12 and 16 are
estimates from one run rather than measurements**, because inventing precise-looking thresholds is
the failure I keep having.

**The readout was breaking the practice it exists to support.** `78%` / `of 25%` / `listening`, in
that vertical order, unlabelled, in an app called OptiListen. His note typed into the app: *"i was
distracted by not understanding or trusting the readout."* Labelled it "of the talking is you" with
"ceiling 25%", separated the practice line, and stored the three-way split so the After screen and
the new detail view show the parts behind the number.

History was a dead end: `Section("Recent")` had no `NavigationLink` while "Still open" three lines
above did. Added `PracticeDetail`, wired both, retired the `Text("Reflection for …")` debug string
that shipped in (4).

Bumped to 2.0 (5), all four files parse-clean on kindbook (syntax only, no SDK), memo to Pard.

## Design pass, ratified and landed

xian on the charm question: *"Ratified. Nice balance of lightweight approach and meaningful
experience improvement. Let's capture these ideas in a doc and iterate one more time, then cut a
release candidate Dan and I can test."*

Spec written first: `docs/design-pass-2026-09-21.md`, with the reframe at the top. **The app is not
too plain, it is undesigned** — every control sat where SwiftUI put it, in system blue, at default
weight. Plain is the right answer for an instrument you set face-up and stop looking at, but it has
to be a decision rather than an absence. Four principles recorded so the next pass does not
relitigate them, and a "deliberately not doing" list (no listening-screen animation, no mascot, no
launch animation, no sound in an app that is listening).

Landed all six: `Theme.swift` with moss/amber as a semantic pair and `.tint()` at the app root; the
End button off filled-destructive-red; the number settling on the existing one-second tick rather
than redrawing every 100 ms; two haptics (first ceiling crossing, loop closed); the Home counter
animating on change; no "0" in 52-point type on first launch. Also took the em dash out of the
empty-state copy, since the plain-language convention applies to product copy.

Pard had not started (5), so this folds into the same build number and **(5) is now the release
candidate for xian and Dan both.** Superseding memo sent, with the two type-check risks named up
front (the `UIColor` dynamic-provider closure, the two-parameter `onChange`).

Six files parse clean. Said again in the memo what the build is actually for: the calibration
thresholds in it are estimates from one field run, and xian's own 9.7 dB outdoor session would now
