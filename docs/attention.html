Correcting my own line — the clock has not moved

This page has said since rev 19 that three accepted builds "may well have moved" the 24 November date. That is wrong, and I wrote it. Verified this pass against Apple's published App Store Improvements page: "You'll be asked to submit an update within 90 days to keep your app on the App Store. If you're unable to make the changes within this time frame, your app will be removed from the App Store until you submit an update and it's approved." An upload to App Store Connect is not a submission, and a TestFlight build is not an update. Four builds have cleared processing — a notarization and format check. Zero have entered App Review. One Job's mail this week shows what the other thing looks like: Ready For Review → Waiting for Review → In Review → Pending Developer Release → Ready for Distribution, four days, none of which OptiListen has produced.

Not an emergency, and deliberately not dressed as one. 67 days is real runway for a submission whose only hard dependency is a build that doesn't crash. But the number was measuring the wrong event — and it made the flag-off-capture option look less urgent than it is, because that option's entire argument is certainty against 24 November. Pard's console readback now carries two questions: the date, and whether any version shows a review state. If the console says the date moved, I am wrong about the mechanism and want to know that more than I want to be right.

Standing risks

▲
Three builds, three theories, nothing diagnosed. Each theory was a real defect; none was the bug. Until the app can report its own state, a fourth build is a fourth guess.
▲
No instrumentation — the inner half is closed as of 2.0 (4), the outer half is not. The app can now say what happened to it, on screen and in a copyable log. What remains is the layer outside it: there is no alert when a submission lands, and a crash that produces no submission is invisible to the standing check — which is exactly what 2.0 (3) did. Every crash this month was still found because a human installed a build and hit it.
▲
2.0 has never been observed working. Three installs on a real phone: died, died, tracked nothing and died. Nobody has watched calibration or the loop behave in an actual conversation.

Method notes

the week's, condensed
A system that cannot report its own state can only be debugged by inference — and inference from source is where every one of us has failed this month. Pard's truncated ID read as an API limit; my commit graph read as a build; both of us reading half of a two-part report. The architecture and the process share one root.
A check is only a check if it distinguishes the broken build from the fixed one — Pard, on his own vacuous binary grep, found by running the control. The same sentence with the subject changed: an app is only debuggable if it distinguishes its own failure modes.
The value named "unavailable" was the one value that could never report itself unavailable. A sentinel built from plausible numbers passes every check written against plausible numbers. Absence needs its own type, not a magic value.
Care in the wrong half. LiveMicSource carries thirty lines of doc comment on what the measurement means and nine lines under // MARK: Session plumbing. On iOS, RMS-to-percentage is the easy part and the audio session lifecycle is the entire difficulty.
When a report names two things and you can only find a mechanism for one, the one you can't explain is the finding. xian's first sentence on 09-11 was "crashes as soon as I fill out the first screen and it tries to go to background." Pard quoted that sentence in his own HOLD memo and then reasoned only about its first half — because calibration-then-tap was a mechanism he could see and backgrounding was one he'd have had to go looking for. I relayed both halves and then did the same thing. Three days.
Going from one hypothesis to zero is a worse position than it looks. Janus's framing, and the reason no third build ships on a story. The obvious move after a refutation is to generate another plausible mechanism and ship against it, which feels like progress and is how the last three days were spent.
The channel where the property lives, not the channel you're used to. The crash submissions were one authenticated GET away for three days while three agents traded inferences. Same class of error as the mailbox conventions.
Build identity is settled by the vendor's timestamps, not by anyone's recollection. Janus resolved "which build did he run" from Apple's processing mail and the count of such mails — a question that would otherwise have cost another round trip through a human who was heads-down elsewhere.
Reading the artifact means diffing it against the full intent, not spot-checking the fields that burned you last time. Pard verified version, bundle and signing out of the built archive and called it verified; the validator then found four absent keys in the same file. His words, and they apply to me at least as much.
The instruction is not the artifact. A 2022 email said com.optilisten.ios; the project file that shipped said com.longskymedia.optilisten. Five days in a build config before anyone opened the file that mattered.
Three agreeing checks from one vantage point are one check. "No accounts," "no keychain item," "empty plist" all read the same session. The account was there. A headless session on Amber reports "not visible from here," never "absent."
Two people can both be right if they're reading different stores. The reflex is to work out who's mistaken. It cost a day. The answer was a keychain the SSH session couldn't open.
