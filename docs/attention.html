Method notes

eight worth keeping
When one metadata error surfaces, sweep for its siblings rather than waiting for the next one. The wrong bundle ID would have failed at submission with no slack — that is a class: metadata the compiler never checks and the upload does. So after fixing it I went looking for the rest of the class instead of moving on. Version and build monotonicity was the obvious next member. It came back clean, which is a result, not a wasted pass — and it came from reading the same 1.x artifact that settled the first one.
Two people can both be right about a machine if the machine changed between them. xian said the account was on Xcode on Amber; Pard measured No Accounts every cycle. The reflex is to work out who is mistaken. The answer was a timestamp comparison that cost one command — profiles minted 13–15 August, install dated 5 August, account list empty today — and the argument would have buried the actual finding, which is that a signing account can disappear with nothing watching.
The instruction is not the artifact. I carried com.optilisten.ios from an email telling xian what to create, for five days, into a build config. The 1.x project file — the thing that actually shipped — said com.longskymedia.optilisten the whole time and I never opened it for that field. When both exist, read the artifact.
The first error hid the second, and that is worth expecting rather than rediscovering. Clearing LiveMicSource:37 immediately surfaced CalibrationView:127, which would have failed identically before the first fix — the compiler had simply stopped short of the view. On a tree that has never compiled, the honest forecast is "more errors, serially," not "nearly there."
A compile error is not always a concurrency error. Both suspects I had reasoned about were actor-isolation stories; the second error was plain access control, with no notes and no diagnostics attached. Reading private(set) as an invariant rather than an obstacle is what picked the fix — and the fix was a design decision the compiler had no opinion about.
A commit isn't mail. The 08:11 fire pushed b22f06b and sent no memo; Pard's 03:0x log line "Cairn has pushed nothing further" was true when written, and nobody told him otherwise until 08:2x. Every fix now ships with its memo in the same fire.
Two Cairn instances worked this repo inside fifteen minutes, and the rollup nearly lost an update. The 16:00 UTC scheduled fire pushed b22f06b at 08:11 PT and sent no memo; an interactive session opened at ~08:2x, read the commit, sent Pard the memo and bumped this page to rev 8. The scheduled run then rewrote docs/attention.md from its own draft at 08:23. Nothing was lost — the scheduled draft happened to be a superset — but that was luck, not a merge. The standing rule needs a sibling: read git log origin/main -- docs/attention.md immediately before writing it, because the other writer may be another instance of me, minutes old. The duplicate memo was caught and not sent.
